# Rust TUI Mechanisms in `xai-org/grok-build`

This analysis is pinned to repository commit **`9684fa3cdbf2995e30ea8b9b637f1db008f144fc`**; all source paths below refer to that revision. The official `xai-org/grok-build` repository describes Grok Build as a Rust, fullscreen, mouse-interactive TUI and licenses first-party source under Apache-2.0. citeturn7search3

A useful architectural distinction up front: the interactive UI is primarily split between `crates/codegen/xai-grok-pager` for application/view/input state, `crates/codegen/xai-grok-pager-render` for drawing and terminal capabilities, and a modified `crates/codegen/xai-ratatui-inline` terminal implementation that exposes information stock Ratatui does not, notably whether a flush actually changed cells. fileciteturn49file0 fileciteturn56file0

## Rendering loop and flicker-free presentation

**Primary paths:** `crates/codegen/xai-grok-pager/src/app/event_loop.rs`, `crates/codegen/xai-grok-pager-render/src/render/draw.rs`, `crates/codegen/xai-ratatui-inline/src/common.rs`, and `crates/codegen/xai-grok-pager/src/app/mod.rs`. fileciteturn4file0 fileciteturn56file0 fileciteturn57file0 fileciteturn49file0

### The scheduler is dirty-state driven, not frame-rate driven

The central event loop is a `tokio::select!`-style reactor. Rendering is mediated by a small `Presenter` object rather than called indiscriminately from every event handler. Its important state is a boolean `dirty`, a sticky `force_full_repaint`, an optional writer sequence currently in flight, the last presentation time, and an optional future time at which a throttled draw should occur. Calling `request()` marks the UI dirty; multiple requests collapse into one pending presentation. fileciteturn4file0

The in-flight field is particularly important. A presentation is allowed only when there is no terminal payload still outstanding and the logical UI is dirty. When a draw submits terminal bytes, the presenter records the output sequence generated by the asynchronous terminal writer. Further state changes can make the presenter dirty, but it does not blindly enqueue another stale frame behind the first one. Once the writer reports that sequence as successfully written, the latest accumulated state can be presented. This is effectively **single-frame backpressure plus state coalescing**. fileciteturn4file1 fileciteturn56file0

Streaming ACP traffic is also paint-rate limited. A state change may call the presenter's throttled-request path; if the minimum draw interval has not elapsed, it records the earliest permissible future draw instead of painting immediately. The explicit rationale in the event loop is to prevent heavy model streaming from starving terminal input processing. Resize bursts are handled similarly but with a dedicated **16 ms resize debounce**. fileciteturn4file4 fileciteturn4file0

**Reimplementation mechanism:** maintain one authoritative model, mark it dirty whenever visible state changes, coalesce dirty notifications, impose terminal-output backpressure, and paint the newest model when the output channel is available. Do not build a FIFO of fully rendered frames.

### “Dirty” does not mean dirty rectangles

Grok Build does **not** appear to maintain geometric dirty regions such as “rows 20–25 need repainting.” The presenter's `dirty` is a whole-view scheduling flag. Once a frame is accepted, the normal UI is logically rendered into the next Ratatui buffer. The optimization happens at the **terminal-cell diff** boundary: the modified Ratatui terminal compares the new buffer against the previous buffer and writes only cells whose terminal representation changed. fileciteturn4file0 fileciteturn56file0

`render/draw.rs` makes the sequence explicit: autoresize the terminal, obtain a frame/back buffer, render, flush the difference between old and new buffers, then swap buffers. It intentionally bypasses Ratatui's ordinary `try_draw()` path. Thus the right conceptual model is:

**full logical recomposition → cell-level diff → minimal terminal writes**, not **widget-level dirty rectangles → partial layout/render**. fileciteturn56file0

A forced full repaint is a different, exceptional operation. The presenter carries `force_full_repaint`; when that flag reaches the rendering path, the terminal is cleared before the normal draw. One use is a focus-regain “heal” when an embedding terminal or multiplexer may have repainted the pane out of band: a same-size resize would not necessarily make Ratatui's autoresize path invalidate everything, so an actual clear is needed. fileciteturn4file1 fileciteturn4file6

### DEC synchronized output is part of every normal frame

The drawing layer wraps a frame in Crossterm's `BeginSynchronizedUpdate` and `EndSynchronizedUpdate`. The repository's own test confirms the emitted byte sequences are exactly:

- begin synchronized update: `ESC [ ? 2026 h`, byte spelling `\x1b[?2026h`
- end synchronized update: `ESC [ ? 2026 l`, byte spelling `\x1b[?2026l`

Those are DEC private mode 2026 set/reset operations. fileciteturn57file0

The synchronized-output protocol's semantics are that the terminal continues parsing incoming operations while showing the previously committed display, then exposes the latest completed terminal-buffer state when mode 2026 is reset. This prevents the compositor from displaying a half-updated TUI frame. The protocol also defines `CSI ? 2026 $ p` as the capability/state query. citeturn8search4

An implementation detail worth preserving conceptually is **what goes inside that transaction**. Grok's draw function does not merely synchronize the Ratatui text-cell diff. Post-cell operations such as terminal image graphics and the final cursor operation are also emitted before synchronized output is ended. That means the text cells, image overlay and cursor relocation can become visible as a single terminal presentation. fileciteturn10file2 fileciteturn37file0

I did **not** find a mode-2026 capability probe on this frame path. The helper queues the synchronized-update commands directly and documents unsupported terminals as gracefully ignoring them. In other words, the code uses DEC 2026 optimistically rather than sending `CSI ? 2026 $ p` and waiting for a response. fileciteturn57file0 The external protocol specification describes the query mechanism, but Grok does not need to use it for its current strategy. citeturn8search4

### Flicker suppression is layered

DEC 2026 is only one part of why the UI behaves smoothly. A second important mechanism is **cursor-command suppression**. Stock Ratatui tends to emit cursor show/hide/move operations every draw; Grok's comments note that those operations reset the terminal's blink timer, so a 30-fps UI can make a blinking text cursor appear permanently solid. `CursorState` remembers the last terminal cursor state and emits nothing when neither cell writes nor desired cursor position require a command. If cells changed underneath a stationary visible cursor, it only repositions it after the diff; visibility commands are limited to actual transitions. fileciteturn56file0

That optimization depends on `xai_ratatui_inline::Terminal::flush()` returning whether any cells were actually written. Consequently, an animation tick whose animated object is off-screen can produce an empty buffer diff and **zero cursor traffic**, rather than disturbing an otherwise idle terminal. fileciteturn56file0

Finally, terminal writes themselves are removed from the Tokio event-loop thread. A complete frame's bytes accumulate in `TermWriter`, are sent through a channel, and a dedicated OS writer thread performs the potentially blocking write/flush to the PTY. The presenter then uses the writer's monotonically increasing completion sequence for its in-flight gate. This prevents a slow terminal emulator from freezing input/model-event processing while simultaneously preventing uncontrolled frame accumulation behind the slow writer. fileciteturn56file0

The overall mechanism an independent implementation should copy is therefore not any particular Rust API but the sequence:

**coalesce state changes → render newest state → diff cells → batch all terminal effects atomically → minimize cursor traffic → serialize terminal presentations behind an acknowledged writer.**

## Mouse routing, focus, and hit targets

**Primary paths:** `crates/codegen/xai-grok-pager/src/app/mouse.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/input.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/interactions.rs`, `crates/codegen/xai-grok-pager/src/views/agent.rs`, `crates/codegen/xai-grok-pager/src/input/mouse.rs`, and `crates/codegen/xai-grok-pager/src/app/app_view.rs`. fileciteturn16file0 fileciteturn22file0 fileciteturn62file0 fileciteturn55file0 fileciteturn23file0 fileciteturn15file0

### Hit testing is based on geometry recorded by the previous frame

There is no DOM-like retained widget tree that receives a mouse event through capture/bubble phases. Instead, rendering computes screen-space `Rect`s and caches them in application/view state. The next mouse event is tested against those rectangles. The most basic example is `PaneAreas`, whose fields hold the latest `scrollback`, `todo`, `queue`, `prompt`, `tasks`, and `catalog` rectangles. Its hit test checks visible nonzero-area optional panes and then the main panes to return an `ActivePane`. fileciteturn55file0

Finer controls use the same idea. The agent state contains small hit-area records and collections of rectangles for things such as buttons, inline-media actions, scrollbars, dropdowns, and other clickable affordances. Inline-media hit targets, for example, are rebuilt from the placements that were actually rendered, so an off-screen item does not retain an active invisible target. Hover state is derived by testing the current mouse coordinate against those rectangles. fileciteturn18file0 fileciteturn39file0

This yields a useful implementation rule: **the renderer is the authority on geometry; input consumes the geometry actually painted, rather than independently recreating layout formulas.** The permission view follows the same principle for variable-height rows: its option hit-testing uses the same row-budget logic as rendering, including expanded/collapsed argument areas, specifically so the visual row and click row cannot drift. fileciteturn28file0

### Routing is ordered from most specific surface to broadest pane

A left-button press is first offered to high-priority, highly specific active surfaces: overlays, close buttons, dropdowns, status controls, media actions, scrollbars and similar cached targets. Many of these checks also ask whether the location is occluded, preventing a control behind another visible surface from accepting a click. Only after those more specific targets fail does routing fall through to `pane_areas.hit_test()`. fileciteturn16file0

At pane level, clicking a Todo/Queue/Tasks/Catalog pane activates that pane and forwards the mouse event to its own handler. Clicking Prompt focuses Prompt and forwards into the prompt editor. Clicking Scrollback focuses Scrollback and begins the scrollback-specific click/selection path, which can subsequently distinguish selection drags, entry clicks, links, expandable entries and other local affordances. fileciteturn16file0 fileciteturn16file3 fileciteturn16file4

This priority structure is effectively an explicit z-order: **modal/special hit targets → pane hit-test → pane-specific content interpretation**. It gives overlays the behavior of modal UI even though the underlying layout still exists.

### Focus is explicit view state

Keyboard focus is represented by an `ActivePane`/`AgentPane` value rather than inferred from cursor location. `set_active_pane()` performs the transition and also handles semantic cleanup, such as closing scrollback search when focus leaves Scrollback. Mouse clicks call this same state-transition path, so click-to-focus and keyboard focus are unified. fileciteturn22file0 fileciteturn55file0

The result is **semantic focus**, not generic widget focus traversal. For example, key handling in Scrollback can resolve Tab to `FocusPrompt`, while visible special panes may alter what Tab means; closing such a pane can deliberately restore Scrollback. The source routes focus actions through explicit application actions rather than asking a generic widget hierarchy for “the next focusable descendant.” fileciteturn63file0 fileciteturn63file5

Blocking cards introduce another focus level. Permissions, question panels, cancellation dialogs and similar surfaces intercept their keys before ordinary pane handling. A permission itself has `PermissionFocus::Options`, `FollowupInput`, or `PatternEdit`, so “focus” is hierarchical in practice: active application view → active agent pane → active blocking surface/mode. fileciteturn61file0 fileciteturn62file0

### Scrolling is routed by pointer location, not keyboard focus

Wheel/trackpad events are intercepted at `AppView` level before normal mouse-click routing. This is deliberate because scroll normalization is considered a property of the physical input device and terminal, not of a particular agent. `MouseScrollState` converts direction-only terminal mouse events into a normalized line delta, maintains stream state, and handles acceleration/device heuristics. fileciteturn15file0 fileciteturn23file0

The normalizer treats closely spaced events as a stream. It has an approximately **80 ms stream-gap boundary**, a default redraw cadence around **16 ms**, and configuration for wheel/trackpad behavior, speed and inversion. Residual movement can therefore be accumulated and emitted on subsequent short scroll ticks instead of forcing a render for every raw terminal event. `tick_scroll()` returns true only when a nonzero line delta was actually dispatched. fileciteturn23file0 fileciteturn15file6

Once a line delta exists, `AgentView::handle_scroll()` hit-tests the mouse coordinate against the same pane geometry used for clicks. A wheel over Scrollback changes scrollback; one over Prompt can be forwarded to the textarea; secondary panes call their local scrolling logic. Modal viewers intercept before this step, and tests explicitly verify that wheel movement does not leak through a modal into the scrollback behind it. fileciteturn20file3 fileciteturn20file0 fileciteturn20file9

At the wire level, these handlers consume Crossterm `MouseEvent`s rather than parsing SGR/X10 bytes themselves. `app/mod.rs` records whether Crossterm mouse capture is active and comments that `EnableMouseCapture` enables five DEC mouse-reporting modes. The repo's routing code therefore intentionally does not contain a second raw mouse-protocol decoder. fileciteturn49file0 I would not attribute literal mouse-enable byte strings to Grok itself: unlike the synchronized-output and graphics sequences below, those bytes are delegated to the Crossterm dependency rather than authored in the examined routing files.

## Panel composition, resizing, and focus traversal

**Primary paths:** `crates/codegen/xai-grok-pager/src/views/agent.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/render.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/panes.rs`, and `crates/codegen/xai-grok-pager/src/app/event_loop.rs`. fileciteturn55file0 fileciteturn40file1 fileciteturn63file0 fileciteturn4file0

The panel system is much closer to a **pure layout solve** than to a desktop GUI container hierarchy. `AgentViewLayoutParams` collects the current screen rectangle, appearance settings and the desired heights of visible regions. `AgentViewLayout::compute()` converts those values into immutable rectangles; shared widgets are then told to paint into those rectangles. The file explicitly describes `AgentViewLayout` as pure screen-area-to-pane-rect computation, with actual orchestration living in `AgentView::draw()`. fileciteturn55file0

The main view is predominantly a vertical stack. It starts with the status bar and optional top panes such as Tasks/Catalog/Todo, reserves a central Scrollback region, then can insert transient regions such as `/btw`, queue, turn status, banners, plugin CTA, follow-up chips and voice-recording status before the prompt; status-line and shortcut rows occupy the bottom. Zero-height optional components are omitted along with their associated gap. The scrollbar/timeline logic subsequently narrows the usable scrollback content rectangle horizontally. fileciteturn55file0

The important resizing rule is that Scrollback uses the layout's protected `Min`, with **five rows** as `SCROLLBACK_MIN_ROWS`; most surrounding surfaces ask for fixed lengths. If the vertical stack becomes overcommitted, the solver therefore protects the principal conversation viewport instead of simply clipping every child proportionally. fileciteturn55file0

There are also explicit degradation thresholds rather than relying entirely on the Ratatui solver. At **16 rows or fewer**, optional rows such as CTA/follow-up content and bottom vertical padding are suppressed so core interaction remains usable. At **20 rows or fewer**, compact rendering is force-enabled as a derived render value; crucially, that does not overwrite the user's persisted compact-mode setting, so enlarging the terminal restores the user's prior preference. fileciteturn55file0

A resize therefore works as follows: Crossterm reports terminal-size activity; the event loop waits for a 16 ms debounce window so a drag does not cause a complete draw on every individual resize notification; the accepted draw calls terminal autoresize; the application recomputes `AgentViewLayout` from the new frame dimensions; rendering then stores the newly computed `PaneAreas`, which automatically becomes the geometry that subsequent mouse events use. fileciteturn4file0 fileciteturn56file0 fileciteturn55file0

This is a strong reimplementation pattern because it prevents a resize-specific state machine from proliferating through widgets. **Size is simply another input to the pure layout function.**

Focus traversal is deliberately independent of vertical layout order. The `ActivePane` enum identifies focusable pane classes, while keyboard handlers and application actions decide where focus moves. Tab from Scrollback may focus Prompt; special panes can interpose their own rules; mouse clicks set whichever pane was hit. Consequently, adding a decorative or transient row to `AgentViewLayout` does not automatically add it to keyboard focus order. fileciteturn55file0 fileciteturn63file0

For an engineer reimplementing this differently, the transferable design is: **make layout a deterministic function from model + terminal size to screen rectangles; make rendering and hit testing consume the same rectangles; keep focus traversal as an explicit semantic graph rather than deriving it from geometric child order.**

## File-edit approval flow

**Primary paths:** `crates/codegen/xai-grok-workspace/src/permission/prompter.rs`, `crates/codegen/xai-grok-pager/src/app/acp_handler/permissions.rs`, `crates/codegen/xai-grok-pager/src/views/permission_view.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/interactions.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/input.rs`, `crates/codegen/xai-grok-pager/src/app/dispatch/permissions.rs`, and `crates/codegen/xai-grok-pager-render/src/appearance/permission_cursor.rs`. fileciteturn58file0 fileciteturn32file0 fileciteturn61file0 fileciteturn62file0 fileciteturn22file0 fileciteturn59file0 fileciteturn33file0

### File approval is a specialization of the generic permission card

There is not a separate retained “file approval widget.” Edit requests come through the same ACP permission mechanism used by shell execution and MCP tools. The pager routes the request by `session_id` to the owning agent, queues it there, and exposes only the **front** `PermissionViewState` as interactive. Later concurrent requests remain FIFO behind it rather than replacing or cancelling the prompt already under review. fileciteturn32file0 fileciteturn61file0

When the request is recognized as a file edit and its raw input contains `file_path`, the display builder constructs the title in the form **`Allow Edit to <path>?`**. Protected-edit metadata can add an explanatory description. This is how the file identity is brought into the generic approval surface. fileciteturn32file0

On the empty→non-empty permission-queue transition, the pager stashes the user's current composer text and clears the prompt area for the permission interaction. If the agent was focused in Scrollback, it remembers that pane and force-focuses Prompt, ensuring the blocking approval is immediately keyboard-reachable. When the queue becomes empty again, the stashed prompt and prior pane can be restored. fileciteturn32file0 fileciteturn59file0

### The widget is an option list with embedded interaction modes

`PermissionViewState` contains the ACP options, currently active option index, title/description, optional scope metadata and scroll/layout state. The renderer takes over the prompt region and lays out the permission chrome, optional provenance/title/arguments and the option rows. If the user moves into free-text rejection feedback, the renderer returns an inline prompt rectangle so the regular prompt widget can be painted inside the permission card rather than duplicating an editor. fileciteturn61file0 fileciteturn26file0

For edit permissions, the shell side has a distinct stable option ID, **`allow-edits-session`**, for “allow all edits during this session.” Its semantics are intentionally session-scoped and in-memory rather than a persisted global edit whitelist. A separate special option ID, **`enable-always-approve`**, represents the much broader “don't ask again for anything” mode. The code relies on exact option IDs, not just the generic ACP `AllowAlways` kind, whenever these scope differences matter. fileciteturn58file0 fileciteturn54file0

That identity separation is a safety mechanism in itself: an `AllowAlways` enum value cannot accidentally acquire edit-session or global-YOLO semantics merely because two options happen to share a protocol-level kind. Dispatch explicitly excludes `allow-edits-session` from the “sticky last permission kind” mechanism so an edit-session decision cannot cause a later unrelated shell permission to preselect that shell prompt's persistent “always allow” row. fileciteturn59file0

### Keyboard interaction

In option mode, row-walk keys, `j`/`k` and arrow keys change `active_idx`. **Enter immediately resolves the currently highlighted option**, and digits `1` through `9` immediately select the corresponding row when it exists. Ctrl-C cancels. Text typed while the RejectOnce row is selected moves the surface into `FollowupInput`, where the regular prompt editor captures an explanatory message; Esc walks back from that mode rather than resolving the permission. fileciteturn62file0

That distinction matters when assessing accidental activation: **the approval flow does not universally require a second keyboard confirmation.** A focused option plus Enter is sufficient. Its explicit anti-misclick measure, discussed next, is on the mouse path. fileciteturn62file0

### Mouse activation deliberately takes two clicks

Permission hit-testing converts the click's screen row into an option index using the rendered permission geometry. On a left click, the first click on a row makes it the active row and records which permission option was clicked and when. A selection action is generated only when a subsequent click is on the **same option row** within the multi-click window. `MULTI_CLICK_TIMEOUT_MS` is **300 ms**. Clicking elsewhere breaks that sequence. fileciteturn28file0 fileciteturn22file0 fileciteturn18file0

So the “approve control” is guarded from an accidental single mouse press by a deliberate **same-target double-click requirement**. This is stronger than a conventional single-click button and also avoids the dangerous interpretation “first click anywhere highlights something; second click somewhere else accepts the newly highlighted row.”

There is, however, an important nuance rather than a blanket claim that approval is double-confirmed. Keyboard Enter remains a single resolution operation. Initial highlighted-row selection is resolved separately by `permission_cursor`: it considers the sticky last confirmed permission type, the configured default, then the special global always-approve row, then index zero. When a concrete sticky/configured permission target is missing, it deliberately degrades toward one-shot `AllowOnce` rather than escalating to the global always-approve row. fileciteturn33file0

At the pinned revision, the effective fallback configuration value represented by `AlwaysAllowAllSessions` means that, in the absence of a more concrete configured/sticky target, the special global always-approve row can be the initially highlighted row. Therefore the source does **not** support the stronger statement “dangerous approval always requires two deliberate gestures”; that is true for mouse activation, not for Enter on the preselected option. fileciteturn33file0

The global option does have additional semantic containment. Its stable ID is treated specially: the shell-side response for the current request maps to a one-shot allow, while the pager separately attempts to turn on its YOLO/always-approve state, drain queued permissions, persist the mode and send its ACP notification. A managed-policy pin may refuse the broad mode transition even though the current request is still granted once. fileciteturn58file0 fileciteturn59file0

**Reimplementation takeaway:** separate permission identity from presentation labels, queue approvals rather than replacing them, show the exact target path, reuse the application's real text editor for rejection feedback, and make high-impact pointer activation require a same-target commit gesture. If stronger keyboard accident protection is desired, that would be a design change relative to this implementation, not merely a reimplementation detail.

## Inline image rendering and terminal graphics

**Primary paths:** `crates/codegen/xai-grok-pager-render/src/terminal/image.rs`, `crates/codegen/xai-grok-pager-render/src/terminal/overlay.rs`, `crates/codegen/xai-grok-pager-render/src/terminal/mod.rs`, `crates/codegen/xai-grok-pager/src/app/agent_view/media.rs`, and `crates/codegen/xai-grok-pager/src/scrollback/wrappers/entry_renderer.rs`. fileciteturn37file0 fileciteturn45file0 fileciteturn38file0 fileciteturn39file0 fileciteturn46file0

### Kitty is the actual graphics workhorse

`GraphicsProtocol` has `Kitty`, `ITerm2`, and `None`, but current terminal-brand policy effectively makes the **Kitty graphics protocol** the supported pixel-rendering path. Kitty, Ghostty and WezTerm map to Kitty graphics. Warp also maps to Kitty for the general graphics capability, although, importantly, the narrower scrollback-overlay policy excludes Warp because the source documents unreliable placement/scrollback behavior there. fileciteturn37file0

The graphics detector is cached via `OnceLock`; it uses Grok's already-built terminal context rather than actively querying Kitty graphics support on every startup. A tmux-backed session is rejected by `graphics_protocol_skip_reason()`. Native Windows is also returned as `None` by the protocol mapping because the code treats ConPTY as unsuitable for passing these graphics control sequences. fileciteturn37file0 fileciteturn38file0

For **scrollback** inline images the allowlist is even narrower: Kitty protocol plus terminal brand Kitty, Ghostty or WezTerm. Warp is purposely excluded despite accepting some Kitty commands because Grok relies on image IDs, placement IDs, z-order, deletion and source cropping to keep pixel graphics associated with the scrolling text grid. Minimal/scrollback-native mode forcibly disables these overlays as well. fileciteturn37file0

This means capability detection is primarily **terminal-brand/environment policy**, not a protocol handshake. That is a meaningful implementation choice: it trades dynamic discovery for known-good behavioral profiles.

### Exact Kitty framing used by Grok

The direct overlay path turns the image into encoded PNG and sends it as base64 Kitty graphics data. The first chunk's control header has the mechanism:

`a=T,f=100,t=d,q=2,C=1,z=<z>,i=1,p=1,c=<cols>,r=<rows>`

and the actual first control sequence has the byte grammar:

`ESC _ G <header>,m=<0-or-1> ; <base64> ESC \`

or, in Rust-style byte notation,

`\x1b_G...;...\x1b\\`.

Continuation chunks use the shorter form:

`\x1b_Gq=2,m=<0-or-1>;<base64-chunk>\x1b\\`

with `m=1` while more data follows and `m=0` on the final chunk. Grok chunks encoded data at **4096 bytes**. fileciteturn37file0

These fields correspond directly to the Kitty protocol: `f=100` is encoded PNG, `a=T` combines transmission and placement, `c`/`r` specify the destination cell rectangle, `z` controls stacking, `C=1` requests no cursor movement, and direct remote data is base64-chunked with no chunk larger than 4096 bytes and `m=1`/`m=0` continuation semantics. citeturn7search4

Grok uses positive z-order for modal image overlays and negative z-order for scrollback imagery so text/dropdown content can appear above inline pictures. Kitty specifies that negative `z` places the image beneath text cells. fileciteturn37file0 citeturn7search4

For persistent scrollback media, the implementation can separate **transmit** from **place**. An image is given a Kitty image ID, transmitted when needed, and subsequent frames can use cheap placement operations rather than retransmitting the full encoded bitmap. Pixel images are independent of the Ratatui cell buffer, so they also require explicit deletion when the owning view disappears or a placement scrolls away. fileciteturn39file0

`terminal/overlay.rs` adds another anti-flicker/performance layer for static modal imagery. It records the current overlay owner and its last geometry. If the same owner is requested at the same position and dimensions on the next frame, it emits **no graphics sequence at all** and leaves the existing pixels in place. Moving/resizing/replacing the overlay causes the required graphics transition. The ownership state is committed only after the post-flush write succeeds, preventing internal state from claiming pixels have changed when terminal I/O actually failed. fileciteturn45file0

### iTerm2 support exists as code but is intentionally disabled by detection

There is a complete iTerm2 OSC 1337 formatter. Its exact emitted form is:

`ESC ] 1337;File=inline=1;width=<cols>cells;height=<rows>cells;preserveAspectRatio=1:<BASE64> BEL`

or byte notation:

`\x1b]1337;File=inline=1;width=<cols>cells;height=<rows>cells;preserveAspectRatio=1:<BASE64>\x07`. fileciteturn37file1

That matches iTerm2's documented OSC 1337 inline-file protocol, where `inline=1` causes display and width/height may be specified in character cells. citeturn7search0

But **current `protocol_for_brand()` maps iTerm2 to `GraphicsProtocol::None`**. The source explains the reason: OSC 1337 lacks the image-ID, z-index, source-cropping and explicit-clear primitives on which Grok's overlay/scrollback model relies, so images cannot reliably track the TUI grid. The helper remains available but ordinary iTerm2 detection chooses text fallback. fileciteturn37file0

That distinction is easy to miss when reading only the enum or the formatter: **implemented protocol formatter does not equal enabled runtime capability.**

### Formats, caching, and fallback

Kitty's direct encoded path accepts PNG. If source content is another decodable raster type, Grok prepares a PNG before it reaches the frame-hot rendering path; on macOS it first attempts conversion through `sips`, with an image-library conversion fallback elsewhere. The comments explicitly keep this conversion work out of the draw path. fileciteturn37file0

Inline-media CPU-side bytes are bounded by a **64 MiB cache**. A missing file can be retried cheaply because the producer may still be writing it, but a decode/load failure is negative-cached against a metadata stamp so a genuinely broken image is not decoded on every animation frame. Kitty IDs are allocated only after valid bytes are available, avoiding a state where later frames attempt to place an image that was never successfully transmitted. fileciteturn39file0

When scrollback graphics are unavailable, the layout does **not** reserve an empty rectangle hoping pixels will appear: `inline_media_rows()` returns zero when the scrollback graphics overlay is inactive. The image module documents the text/metadata fallback, and minimal mode explicitly uses an `[Open …]`-style text affordance rather than blank image rows. fileciteturn46file0 fileciteturn37file0

There is **no Sixel path** in the examined graphics protocol abstraction: runtime choices are Kitty, the currently gated-off iTerm2 formatter, or no pixel protocol. fileciteturn37file0

A reimplementation can therefore copy the deeper pattern without copying the protocol choice: **separate terminal capability policy from image encoding; reserve layout only when graphics will actually be painted; transmit large image data independently from cheap placement updates; explicitly own/delete graphics that live outside the text grid; and put graphics escapes in the same synchronized presentation transaction as the text frame.**

## Idle behavior and redraw discipline

**Primary paths:** `crates/codegen/xai-grok-pager/src/app/app_view.rs`, `crates/codegen/xai-grok-pager/src/app/event_loop.rs`, and `crates/codegen/xai-grok-pager-render/src/render/draw.rs`. fileciteturn15file0 fileciteturn4file0 fileciteturn56file0

The TUI does not use a perpetual 30- or 60-fps redraw loop. `AppView` publishes a three-level `TickDemand`: **`None`**, **`Slow`**, or **`Fast`**. `None` means no animation/polling tick is required. `Slow` is used for inherently low-rate visible work such as the welcome-logo shimmer and a macOS modifier/link-hover poll. `Fast` is requested by real animation or short-latency state machines. fileciteturn15file0

`Fast` uses the configured animation interval; the source describes the normal default as about **30 fps**. `Slow` is bounded to at least **83 ms** between ticks, approximately 12 fps, specifically so a visually almost-idle welcome screen does not run the full animation cadence. fileciteturn15file1

`tick_demand()` is model-driven. Examples that can demand fast ticking include an active turn animation, pending cancellation reconciliation, pending actions that expire, voice listening, active image loading/playback, asynchronous edit highlighting, Mermaid rendering and similar live state. An ordinary stationary agent view with none of those conditions can return `None`. fileciteturn15file1 fileciteturn15file2

The event loop turns that demand into an optional deadline. When no animation tick is armed, the future participating in `select!` is effectively `std::future::pending()` rather than a short repeating sleep. After an animation tick fires, the arm is cleared, `app.tick()` runs, and a presentation is requested only if the tick actually changed visible state; the next tick is armed only if the updated model still demands one. fileciteturn4file3 fileciteturn4file9

Scroll inertia/residual normalization follows the same discipline. A short scroll cadence is active while there is a scroll stream to service, but `tick_scroll()` only marks the frame dirty when it emits an actual line movement. When the stream ends, its state is cleared rather than leaving a forever-running scroll timer. fileciteturn15file6

Normal redraws are therefore triggered by **observable state transitions**: input that reports `needs_draw`, ACP/model events that alter visible state, completed asynchronous tasks whose result changes a view, an accepted resize, an animation tick that advances something, a normalized scroll delta, configuration/theme changes, modal state changes, hover transitions and similar events. They are not triggered merely because “another frame period elapsed.” Heavy streaming events additionally go through the presenter's paint throttle and coalescing described earlier. fileciteturn4file4 fileciteturn4file6

The code even treats some polling as a free rider on existing wakeups. For example, the clipboard focus-tip poll is run when the event loop is already awake for real input and is explicitly described as **never being scheduled by its own idle timer**. fileciteturn4file6

There are two further idle wins after a draw has already been requested. First, a logical redraw whose new Ratatui buffer is identical to the previous one creates an empty terminal-cell diff, so no content bytes need be written. Second, when that happens and the cursor state also has not changed, Grok sends no cursor command either. When there is no draw call at all, `render/draw.rs` explicitly notes that nothing is sent and the terminal's normal cursor blink proceeds undisturbed. fileciteturn56file0

The writer side does not require the event loop to wait for PTY availability: the terminal writer thread blocks on its channel/terminal I/O while the async reactor remains free. Combined with the presenter's one-in-flight-frame gate, a slow terminal produces **coalescing**, not an ever-growing backlog of rendered intermediate states. fileciteturn56file0

The idle mechanism can therefore be summarized as:

**No visible work → no animation deadline → reactor blocks on real events.  
Low-frequency visible work → slow deadline.  
Active animation → fast deadline.  
State unchanged after a tick → no draw request.  
Draw accepted but cells unchanged → no cell output.  
Cells and cursor unchanged → no cursor output.  
Terminal slow → writer blocks, model events continue, intermediate frames coalesce.**

That combination—rather than any single optimization—is the TUI's core idle-CPU and low-jitter discipline.
