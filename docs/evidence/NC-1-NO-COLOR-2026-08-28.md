## Scope and policy boundary

NC-1 treats `NO_COLOR` as a rendering preference, never a terminal
capability. A set, non-empty value selects the already-shipped monochrome tier
when board, live-map, or replay code chooses its default tier. An unset or empty
value preserves the existing color decision. Explicit `color` and `color_tier`
arguments remain authoritative overrides.

Production edits are limited to `floati/tui.py`, `floati/tui_chart.py`, and
`floati/replay_render.py`. No capability-model, wake, daemon, CLI-dispatch, bus,
machine-output, copy, or renderer-palette file was edited. The default demo path
uses `run_board` and therefore inherits the board policy; explicit demo capture
choices remain overrides.

## RED-first receipt

Before production edits, the four Regatta/demo modules ran 52 tests with three
failures. Each failure showed the same root cause: the default-tier predicates
tested environment-key presence, so `NO_COLOR=""` incorrectly selected
`mono` for the board, live map, and replay. The replay failure also proved that
the rendered empty-value bytes differed from the unset bytes.

The minimal repair changes those three predicates from presence to value
truthiness. It adds no capability state and does not modify the existing
monochrome renderer.

## Behavior proved

- `NO_COLOR=1` leaves terminal protocols active but emits zero SGR bytes from
  board, live-map, and replay surfaces; glyph twins and visible text remain.
- `NO_COLOR=""` produces the same default tier as unset for board and live map,
  and replay output is byte-identical between empty and unset environments.
- Explicit live-map `color_tier="256"` overrides `NO_COLOR=1` and emits the
  existing 256-color tier.
- Explicit demo `color=True` overrides `NO_COLOR=1`; its current bytes remain
  pinned at SHA-256
  `cef93c3213392432e10732aff4967c531fe4ef39223fb02b57580077728ec25c`.
- Existing plain/JSON machine twins remain in the focused Regatta banks.
